# Research: Firewall Security Faceoff · First Playable

Phase 0 output. The Technical Context had no open unknowns after clarification, so this file
records the design decisions that had real alternatives.

## 1. Stack

- **Decision:** semantic HTML, CSS, and native JavaScript modules, with no framework, bundler,
  or package install.
- **Rationale:** the starter plan's default; the constitution requires a self-contained static
  game; six views and one rule table do not need a framework.
- **Alternatives considered:** a component framework (adds a build step and a dependency to
  review within a 60-minute build); a canvas or 3D renderer (works against keyboard access and
  text equivalents).

## 2. How rule reordering works

- **Decision:** Move Up and Move Down buttons on each rule, plus Remove. No drag and drop.
- **Rationale:** constitution IV requires a keyboard equivalent for reordering. Buttons are the
  keyboard equivalent, so building drag and drop as well would be a second input path to test.
- **Alternatives considered:** drag and drop with a keyboard fallback (two implementations of
  one action); a numeric position field (free-form entry, forbidden by FR-007).

## 3. Test runner

- **Decision:** one set of test files, two entry points: `tests/index.html` in the browser and
  `node tests/run-node.mjs` on the command line. A small shared `harness.js` provides `test`
  and assertions. The runner loads `levels.json` (by `fetch` in the browser, by file read in
  Node) and hands it to the tests.
- **Rationale:** the starter requires a dependency-free browser runner; constitution VII
  requires reproducible commands. Engine modules are pure and import nothing from the DOM, so
  the same files run in both places.
- **Alternatives considered:** browser only (not runnable from a terminal); a test framework
  from a package registry (adds an install step and a dependency); Node's built-in runner only
  (drops the starter's browser page).

## 4. Where expected results come from

- **Decision:** `tests/cases.js` holds the spec's 34 cases as literal data: level, tier, rule
  base, and the expected outcome, deciding rule positions, breach steps, and score.
- **Rationale:** constitution I requires expected results recorded independently of the
  implementation. Copying them from the spec, where they were worked by hand, is that record.
- **Alternatives considered:** snapshot tests generated by running the engine (circular: they
  would pass for any engine).

## 5. Rival results and solvability

- **Decision:** `levels.json` stores each rival's rule base and each challenge's
  `referenceSolution`, and nothing derived from them. The engine computes the rival's breach
  step and score. Validation requires the rival to pass the service check and be breached, and
  requires the reference solution to complete the level.
- **Rationale:** constitution VI forbids an answer key that overrides the engine, and FR-034
  requires rejecting an unsolvable or unbeatable level. Validating a stored solution through
  the engine does both without a search.
- **Alternatives considered:** exhaustive search for a completing rule base (nearly a million
  orderings for nine rules before control settings); storing the rival's score and breach step
  in data (an answer key).

## 6. Address matching

- **Decision:** addresses are exact host strings. `null` in a rule field means any.
- **Rationale:** every shipped rule names a single host or any. Subnet matching would add
  parsing and boundary cases with nothing to exercise them.
- **Alternatives considered:** CIDR matching (needed only if a future level teaches prefix
  scope; that would be a new spec).

## 7. Explanation text

- **Decision:** the engine returns structured evidence and stable reason codes.
  `engine/feedback.js` turns them into sentences from templates. Lesson text specific to a
  level (why an attack matters, what misconception a mistake shows) is authored in
  `levels.json` on the attack step, probe, or challenge.
- **Rationale:** constitution VI requires feedback to agree with the evaluator's reasoning, so
  the sentence naming the deciding rule must be generated from the result, not hand-written.
  Authored lessons stay editable as content.
- **Alternatives considered:** fully authored feedback per wrong answer (cannot cover every
  rule base a player can build, and could contradict the engine).

## 8. Turn-by-turn display

- **Decision:** the full result is computed on submit. The result view reveals one attack step
  per press of Next Attack, with Show Full Results always available. With reduced motion
  requested there are no transitions.
- **Rationale:** FR-040 forbids animation delaying results. Making the turns a user-paced
  reveal keeps the turn-based feel without timers.
- **Alternatives considered:** timed automatic playback (delays feedback and needs pause
  controls).

## 9. Detecting an identical resubmission

- **Decision:** a submission is serialized to a canonical string of ordered rule IDs with their
  control settings. The state module compares it to the last failed submission for that level
  and tier.
- **Rationale:** FR-026 says an identical resubmission of a failed rule base is not a new
  attempt; a string compare is sufficient because rule IDs are stable.
- **Alternatives considered:** comparing results (two different rule bases can give the same
  result and should each count).

## 10. Vendor-neutrality check

- **Decision:** `content.test.js` scans every string in `levels.json` against a short list of
  firewall vendor and product names kept in the test file. `index.html` is read by eye.
- **Rationale:** SC-006 is a zero-occurrence criterion, which a scan checks cheaply. The list
  lives in tests, so it is not shipped game text.
- **Alternatives considered:** manual review only (easy to miss in six challenges of content).
